# Governance

## Principle

The project is designed for **maximum autonomous execution inside bounded human authority**.

The human owner should not become routine middleware.

## Human role

The owner retains:

- root authority;
- veto / stop / override;
- reserved constitutional decisions;
- irreducible provider-required human acts;
- ownership and extraordinary capital decisions.

The owner is not intended to be the normal:

- dispatcher;
- campaign manager;
- repair technician;
- prompt router;
- browser operator;
- approval engine for routine authorized work.

## CEO role

Inside enacted authority and passing gates, the CEO should act.

That can include ordinary operating work such as:

- research;
- strategy;
- prospecting;
- sales and follow-up;
- pricing within enacted economic limits;
- customer communications;
- delivery coordination;
- invoicing / receivables / payables within authority;
- workforce management;
- deployment and maintenance;
- marketing;
- scheduling;
- model routing;
- recovery from ordinary production defects.

## Protected boundary

The CEO and lower layers may **not** autonomously redefine:

- constitutional authority;
- owner root/veto;
- root authentication or recovery;
- mechanisms that expand CEO authority;
- protected audit requirements;
- ownership boundaries;
- extraordinary capital authority.

## Load-bearing rule

> **The loop may optimize execution. It may not optimize or expand its own authority.**

## Optimization authority

Optimization is subordinate to existing operating authority.

An agent, executive or optimization loop may improve execution tactics only inside an already-enacted authority envelope. Optimization does not create authority.

Permitted optimization targets can include:

- models and routing;
- prompts;
- routines;
- cost allocation;
- retry / recovery tactics;
- worker selection;
- execution sequencing;
- bounded tool usage.

The optimization loop may not autonomously alter:

- constitutional authority;
- owner root / veto;
- root grants;
- protected destinations or resources;
- delegation ceilings;
- protected audit requirements;
- mechanisms that expand the optimizer's own authority.

A consequential optimization is not accepted merely because its author reports improvement. The intended governance contract is:

```text
before state / metrics
→ proposed bounded change
→ authority check
→ protected invariants
→ change
→ independent re-verification
→ accept / reject / rollback
→ durable evidence
```

The verifier should be able to establish both the intended improvement and the absence of material regression in protected invariants.

This extends the load-bearing rule:

> **The loop may optimize execution. It may not optimize or expand its own authority.**

## Delegated authority

MetaBot treats delegation as a bounded transfer of existing authority, not as a way to create new authority.

The intended runtime chain is:

```text
root principal
→ agent identity
→ parent grant
→ delegated child grant
→ attenuated scope
→ action/resource/destination constraints
→ policy decision
→ execution
→ verified outcome
```

Rules:

- every consequential actor should identify the principal it represents;
- every delegated consequential action should be traceable to a parent grant;
- a child delegation must never exceed the parent grant;
- the CEO cannot manufacture authority by delegation;
- C-suite executives cannot manufacture authority for workers;
- conversational confidence is not authorization;
- external protocols, gateways and remote peers do not become sources of constitutional authority;
- owner root/veto remains protected across every delegation hop.

Within existing authority, the expected behavior is **execute and report**, not **ask for redundant approval**. A conversational surface such as Telegram must not recreate a human approval checkpoint for work already authorized to the CEO or C-suite.

### Destination constraints

For network-capable tools and agent protocols, authorization should include the remote destination as part of the decision.

An otherwise permitted action does not imply permission to send credentials, requests or agent traffic to arbitrary discovery URLs, loopback/internal metadata targets, credential endpoints or unregistered remote peers.

## Fail-closed behavior

If authority for a consequential action is:

- missing;
- ambiguous;
- stale;
- contradictory;

the affected action should stop or degrade safely.

That does **not** require stopping unrelated work.

## Consequential does not mean owner-approved

A consequential action can still be ordinary CEO authority if that authority has already been enacted.

The system should not recreate a human approval loop merely because an action matters.

## Irreducible human act

When a provider or law genuinely requires a person:

1. prepare everything possible;
2. reduce the request to the smallest exact human step;
3. surface it once with evidence;
4. continue unrelated work.

## Evidence discipline

The project distinguishes:

- **FACT** — explicitly established by reliable evidence;
- **DECISION** — intentionally enacted choice;
- **INFERENCE** — reasoned conclusion;
- **UNKNOWN** — not established;
- **HISTORICAL** — once true or claimed, not automatically current.

A successful unit test is not automatically live runtime proof.

A configured integration is not automatically runtime-usable.

A provider-accepted send is not automatically recipient delivery.
